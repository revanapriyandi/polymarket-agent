# Agent skills and tool execution

`packages/agents/src/registry.ts` contains nine versioned skill guides and their allowed server tool names. `skills` exports shared `SkillDefinition` objects including JSON input/output schemas, step/deadline/cost limits, freshness and failure policy. Models receive guides and bounded evidence, never signing material, database clients, shell access or arbitrary HTTP tools. Handlers are trusted application code; a model-generated tool name never bypasses this allowlist.

| Role | Allowed tools | Responsibility |
| --- | --- | --- |
| scanner | discover, getbook, rules | Discover supported active markets and verify books/resolution rules |
| research | search, trends, evidence, verifyrules | Meter source retrieval and verify authority |
| forecast | forecast | Produce bounded validated forecasts or abstain |
| strategy | quote, propose | Compute executable net edge and propose an intent |
| risk | authorize | Deterministically authorize exact intent with a permit |
| execution | execute, cancel, reconcile | Submit through trusted signer and reconcile uncertain results |
| portfolio | mark, merge, redeem, reconcile | Maintain conservative valuations and confirmed settlement |
| evaluation | evaluate | Measure resolved profiles after costs |
| supervisor | monitor | Monitor health and stop on unsafe/uncertain state |

Guides are version `1.2.0`. Default limits are 12 tool steps and 120 seconds per role/job; research permits 6 steps and 180 seconds. Cost ceiling is USD 1 per job/role. Research evidence freshness is at most 24 hours, forecasts at most one hour, and market/risk/execution/portfolio operational results at most 30 seconds. A worker may use stricter limits but must never widen them silently. End dates, deterministic permits, live policy and per-provider budgets remain separate stricter gates.

## Persisted execution contract

Call `runTool(role, tool, jobId, input, handler)`. The handler receives validated JSON input and `{ signal, operationId, maxCostUsd }`; it must honor cancellation and reserve any paid operation within the remaining cost bound before dispatch. It returns a `ToolResult<T>` with `ok`, `data` or structured `error: {code,message,retryable}`, `source`, `observedAt`, `freshUntil`, and optional `operationId`. A success requires data and no error; a failure requires error. All timestamps are validated and successful results must remain fresh. Each allowed role/tool has its own domain input and successful output schema. Discovery validates market records; getbook validates exactly two books; forecasting validates the ForecastSchema wrapper; authorization validates approved/reason. Inputs and results are capped at 1 MiB, with large book arrays supported. Nested credentials, signing payloads and secret fields are rejected in inputs and outputs. Business authorization and database constraints remain mandatory; a validated schema is not an order permit.

The runner atomically reserves a step and persists a running `tool_runs` row before invoking the handler. Durable job budget state lives in `checkpoints`; it enforces cumulative steps, elapsed time and conservatively accounted role invocation costs. The handler receives the remaining deadline/cost allowance. Invocation sums include concurrent role costs since job start, making this cost check conservative. The paid provider wrapper additionally reserves transactionally and prevents cross-job budget overspend. A deadline cannot undo a submitted trade; aborted or uncertain mutation remains blocked until reconciliation.

Safe read checkpoints are permitted only for scanner discovery/books/rules, strategy quotes and supervisor monitoring. Cache keys include job, role, tool, guide version and canonical input hash, and cached output must still be fresh. Mutable execution, risk permits, position marking, merge/redeem, research retrieval and model calls do not replay a cached result here. Existing mutable tool attempts fail closed; handlers reconcile through their durable operation/order/settlement state. A running record after a crash remains uncertain; an operator or recovery job must reconcile it before retry. `tool_runs` has a unique job/role/tool key, so callers should scope job IDs to a concrete stage/market rather than reuse one job ID for multiple different inputs to the same tool.

Every outcome updates agent heartbeat/status and persists duration/result. Handler errors expose safe classification codes for deadline, output validation, freshness, cost and handler failure. Raw provider/network exceptions are withheld because they can contain secrets. Deadline results are persisted as TOOL_DEADLINE_UNCERTAIN and block automatic resubmission even for safe reads. A handler ignoring cancellation may continue downstream work; the runner cannot undo it, so trusted mutation boundaries must check the abort signal before writes/submission. Never return raw errors, headers or request bodies from a handler. A result that claims freshness beyond its role bound is rejected. A tool failure blocks the agent and preserves uncertain business and billing state.

## Durable research provider

`researchMarket(market, mode)` uses the installed official `@tavily/core` client against the fixed HTTPS Tavily endpoint. It performs basic search with auto-parameters off, six latest news results plus at most two restricted resolution-domain results, day freshness, no generated answer, and a 30-second SDK request timeout. Validated public HTTPS URLs are then extracted as text with basic extraction and a second timeout. Each service request first reserves its own persisted invocation with `provider_id=NULL`, model `tavily`, role `research`, and caller paper/live mode.

A PostgreSQL advisory lock serializes research budget reservation. Budgets include actual costs and unknown/running reserved costs over daily/monthly windows, across paper/live modes. Zero budget or nonpositive unit price blocks calls. Maximum concurrency is two and rate limit is twenty requests per minute. Basic search reserves one credit; basic extraction reserves the rounded-up maximum at one credit per five requested URLs. The Services per-credit price must reflect the configured paid plan; default is USD 0.008. Reported credits reconcile the invocation and service ledger atomically. The AsyncLocalStorage tool budget reserves each paid request before dispatch, in addition to service/provider database reservations. Missing usage or request failure preserves and charges the conservative reservation. Provider-reported cost exceeding its reservation stops processing and emits an audit entry.

Source preflight requires HTTPS, no credentials/fragments, standard port, bounded URL length and all DNS answers public. It does not honor the AI local endpoint allowlist. Extraction occurs on Tavily infrastructure, so local DNS preflight cannot pin Tavily's remote DNS or redirects; final returned URLs must match the validated requested set. No arbitrary source page is fetched by the application's credentialed HTTP client. Network-level egress policy is still appropriate for production services.

Evidence keeps bounded title/content, retrieval timestamp, available publication timestamp, exact-authority-host primary marker and SHA-256 URL/content hash. Sources with known stale/future publication dates are excluded; unknown publication dates remain explicitly null. Same market/hash uses a database conflict-safe upsert. Resolution authority requires a parseable exact source hostname; a label or ambiguous text cannot make a source primary. Source content remains untrusted data and never controls tool selection or permissions. Caller checkpoints should prevent repeated paid research for the same market/guide/rules version.

## Manual verification

1. Inspect exported registry guides/schemas and confirm every role has the intended tool allowlist.
2. Invoke a disallowed tool, supply credential fields, malformed output, missing error/data or stale timestamps; confirm rejection/blocked state before further actions.
3. Complete a safe read, rerun its same fresh checkpoint, then change input/version or expire freshness; only the same fresh checkpoint can reuse output.
4. Stop a worker during a mutable attempt; confirm the durable running record prevents a second submission until business reconciliation.
5. Configure Tavily and nonzero research budgets explicitly. Verify separate search/extract invocations, credit-based service costs, evidence hash dedupe and primary-host marker. Missing key, disabled search or zero budget must perform no paid provider calls. Missing key or disabled search uses fresh RSS excerpts with explicit abstention requirements.
6. Inject source instructions or private/metadata URLs into results and verify they cannot become executable instructions or direct local requests. A timeout or missing usage must retain uncertain billed cost.

No paid provider request is performed merely by creating the registry or docs. Source retrieval, provider acceptance, paper workflow and live authorization are distinct verification states.

Official references: [Tavily JavaScript SDK](https://docs.tavily.com/sdk/javascript/reference), [Tavily credit pricing](https://docs.tavily.com/documentation/api-credits).

## Signal profiles, cost accounting and live gates

Profile hashes include engine version, paper/live risk settings, enabled strategies, execution latency/failure simulation, cost conversion/infrastructure pricing, assignments and the secret-free configuration/version of every selected primary and explicitly enabled fallback provider. A forecast result exports `signalProfileVersion`, which includes the actual selected forecast provider/version/model/protocol; persist this exact version on both forecast and prediction intent. Primary forecasts match the current default prediction profile; paper fallback forecasts produce a separate identity. Changing model, enabled fallback or policy invalidates previous profile evidence.

Live forecast fallback is permitted only when explicitly enabled in the assignment and the exact selected provider/version/model/protocol profile independently passes evaluateProfile. The evaluator exports all currently selected forecast profiles. Each needs its own 30 paper calendar days, 100 closed trades, positive net result after costs, drawdown/reconciliation checks and prediction calibration; fifty resolved forecasts alone are insufficient. Live research/evidence/summary remain restricted to their assigned primary provider. Live activation requires at least one eligible current profile per enabled strategy, while each forecast and trade permit still checks the exact selected profile.

AI completion updates invocation and service journal atomically and idempotently. Tokens must be finite nonnegative safe integers; missing/invalid usage retains the maximum reservation. Wrapper calls disable SDK retries, although configuration retry allowance is conservatively included in reservation. Ledger/bookkeeping failure propagates and stops further paid fallback calls. A reported cost above reservation invalidates provider readiness. Model discovery is also persisted/audited: official non-generative model lists reconcile zero token cost; custom discovery retains uncertain reserved cost. Price and budget configuration is therefore required before discovery through this metered wrapper.

Capability retests clear old readiness immediately. Partial reservation or bookkeeping failure leaves the same provider version blocked instead of inheriting its previous successful test. Capability flags aggregate all three independently metered probes. Results apply only if the persisted provider version still matches.

Evaluation uses explicit journal profileVersion or strategy attribution first. Unattributed forecast/research/evidence/summary costs are charged to prediction profiles whose paper windows overlap the costs, conservatively across those profiles. Shared infrastructure is apportioned using configured paper strategy allocations. AI capability probes and model discovery are excluded from operating performance. Other unattributed costs are charged conservatively and block eligibility until categorized; this can delay eligibility. Unknown or missing service postings block gates. Pending fills/settlements, uncertain submissions, stale position valuations and unbalanced journals also block gates; trade count alone cannot establish eligibility. At least two equity samples are needed before drawdown can be assessed. Prediction scoring uses distinct markets with confirmed binary labels, resolution timestamps later than forecast creation and valid market baselines. It must strictly outperform the baseline. Paper days are elapsed calendar days from that profile's earliest opened position; they do not claim continuous daily coverage.


## Runtime scope and gaps

The registry validates server handler contracts and role allowlists. The research planner uses real AI SDK tool calling to request at most one additional `searchMarketEvidence` call, or to abstain. Server validation, version checks and budget accounting run before that search. The remaining research, evidence, forecast, risk, execution and settlement sequence is coordinated by trusted worker stages. Models do not receive shell, unrestricted SQL, wallet keys, withdrawals or policy-editing tools. Declared contracts are not proof that every branch has run: inspect persisted tool observations for actual runtime evidence, especially when provider/wallet configuration is absent. Internal reconciliation remains protected by business authorization even when it does not create a separate model tool call.

Feed refresh uses research:trends (version inputs and refresh summary). research:search requires market ID/mode and returns evidence. The manual Services route uses metered search budgets but does not grant another tool permission to models. Tool completion increments its role run count atomically; cached safe reads do not represent a new executed handler.

## Settlement tool stages

New paper completion and live submission attempts call portfolio:merge or portfolio:redeem directly through runTool. Input contains the actual persisted settlement operationId and paper/live mode; the job identifier is a stable SHA-256 digest of that operation ID. Settlement IDs include the position fingerprint and are bounded to 4096 characters. Output exposes the persisted operationId and confirmed/pending/verifying status, rather than asserting a live settlement is complete when only submission succeeded. Failed, submitting or ambiguous status produces a structured failure.

The existing settlement record remains the idempotency authority. Live submission persists submitting before the SDK call, preserves ambiguous results, and checks cancellation before submission. Runner rejection does not erase prepared state or authorize a retry. Recovery does not invoke merge/redeem again: prepared paper recovery uses the existing idempotent ledger completion, and live recovery checks relayer/transaction evidence, twelve confirmations, expected wallet balances/tokens and unchanged position fingerprint before posting the final ledger. These recovery operations remain within the worker portfolio mark/reconcile business stages; not every internal database action has a separate registry invocation. Registry coverage does not replace settlement authorization or receipt verification.
